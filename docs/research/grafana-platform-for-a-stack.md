# O que o Grafana da plataforma CodeLab aceita de um Application Stack

Data: 2026-10-20

## Pergunta

Ticket #70, filho do mapa #69 ("Visualizar a Personal Health History no Grafana"). O que o Grafana da plataforma CodeLab aceita e impõe a um Application Stack que queira publicar dashboards sobre o PostgreSQL? Em particular:

1. Um stack pode declarar a própria datasource PostgreSQL, ou só a plataforma pode? Como ela é provisionada e onde a senha fica?
2. O Grafana alcança o container `postgres-postgres-1` pela rede? Por qual host e porta?
3. Formato e localização de `observability/dashboards/*.json`: pasta, UID, título, convergência e o que acontece com uma edição feita na UI.
4. Versão do Grafana, painéis disponíveis (Geomap, State timeline, Bar chart, Time series) e plugins permitidos.
5. Permissões: pasta, organização e quem vê os dashboards do stack.

## Resumo

- **Um stack não declara datasource nenhuma.** A geração que o stack publica só tem `dashboards/*.json`, `alerts/*.json` e `services.json`; datasources são provisionadas por arquivo, pela plataforma, a partir do `codelab/infra`. Hoje existem só `prometheus` e `loki`. Confiança: alta (código).
- **Pior: o contrato atual proíbe consultar qualquer outra datasource.** O reconciliador recusa a geração inteira se qualquer `datasource`/`datasourceUid` de um dashboard ou regra tiver UID fora de `prometheus`, `loki` e `__expr__`, e também recusa variável de template do tipo `datasource`. Um dashboard sobre o PostgreSQL do `myhealth` hoje é rejeitado na fase `validate`, e **a rejeição impede o deploy do runtime da API**. Confiança: alta (código, testes e ADR-0008).
- **O Grafana não alcança o PostgreSQL hoje.** O Grafana está nas redes `web` e `observability`; o PostgreSQL só na rede `postgres` e em `127.0.0.1:5432` do host. O nome alcançável seria `postgres:5432` (ou `postgres-postgres-1:5432`) dentro da rede `postgres`, à qual o Grafana não pertence. Confiança: alta (compose).
- **Portanto, dashboards sobre o `read_model` exigem mudança na plataforma**, em três pontos: ligar o Grafana à rede `postgres`, provisionar uma datasource PostgreSQL com a conta `myhealth_read`, e emendar o ADR-0008 para que o reconciliador aceite o UID dessa datasource (de preferência só para o app `myhealth`). Isso é inferência do que foi lido, não decisão registrada.
- **Formato:** JSON nativo do Grafana, um dashboard por arquivo em `observability/dashboards/*.json` (sem subpastas), com `uid` local obrigatório (`[A-Za-z0-9_-]+`, no máximo 30 caracteres para `myhealth`, porque vira `myhealth--<uid>` com limite de 40). O título é livre. A pasta é imposta: UID `codelab-app-myhealth`, título `App: myhealth`. Confiança: alta.
- **Convergência:** a cada deploy e a cada 30 segundos, pela API do Grafana, com `editable: false` forçado e um hash de conteúdo numa tag `codelab-content-<hash>`. Arquivo removido do repositório é dashboard removido do Grafana. Uma edição na UI que mexa nas tags é desfeita em até 30 segundos; uma que preserve as tags não é detectada pelo reparo (ver "Lacunas"). Confiança: alta para o mecanismo, média para o caso da edição na UI.
- **Versão:** imagem `grafana/grafana:13.1` (tag flutuante de patch). Na 13.1 o PostgreSQL é datasource embutida, e Time series, Bar chart, State timeline e Geomap são visualizações embutidas. Nenhum plugin é instalado pela plataforma; o reconciliador não restringe tipos de painel. Confiança: alta para a tag e para os painéis; o patch exato em execução não foi verificado.
- **Permissões:** o reconciliador cria a pasta pela API sem definir permissões, na organização do usuário `admin` (na prática a org principal). O acesso externo passa pelo Cloudflare Access, que só permite o e-mail do operador, e depois pelo login nativo do Grafana, com cadastro e acesso anônimo desligados. Na prática só o operador vê. Confiança: alta para o perímetro; média para as permissões padrão da pasta.

## 1. Datasource: quem declara, como é provisionada, onde fica a senha

### O que as fontes dizem

- A geração lida pelo reconciliador tem exatamente três entradas: `dashboards/*.json`, `alerts/*.json` e `services.json` (mais o marcador `tombstone`). Nada mais é interpretado ([reconciliador, `read_generation`, linhas 170-197](https://git.codelab.tec.br/codelab/infra/src/commit/41e02eb8703dc77865ffd1ddea3062195ab6e037/ansible/roles/observability_reconciler/files/codelab-observability-reconcile)). A `deploy-stack` só copia `dashboards/*.json` e `alerts/*.json` de `observability-dir` (padrão `./observability`) para a geração ([ds:`bin/deploy.sh`, linhas 133-156](https://git.codelab.tec.br/codelab/deploy-stack/src/commit/fa82c373cb1b4c87135013690ebde72caf28c2c4/bin/deploy.sh); [ds:`action.yml`](https://git.codelab.tec.br/codelab/deploy-stack/src/commit/fa82c373cb1b4c87135013690ebde72caf28c2c4/action.yml)). Não existe superfície para um stack declarar datasource.
- A lista de datasources permitidas é fixa no reconciliador: `ALLOWED_DATASOURCES = frozenset(("prometheus", "loki", "__expr__"))` ([reconciliador, linha 61](https://git.codelab.tec.br/codelab/infra/src/commit/41e02eb8703dc77865ffd1ddea3062195ab6e037/ansible/roles/observability_reconciler/files/codelab-observability-reconcile)). `_check_datasources` percorre o JSON inteiro de cada dashboard e regra e rejeita qualquer `datasource` ou `datasourceUid` cujo UID não esteja na lista; `_reject_datasource_variables` rejeita variável de template `type: datasource` (linhas 228-251 e 285-291). Os testes confirmam que `grafana`, `postgres-admin` e `${DS_PROMETHEUS}` rejeitam a geração ([infra:`tests/test_observability_reconciler.py`, classe `Datasources`](https://git.codelab.tec.br/codelab/infra/src/commit/41e02eb8703dc77865ffd1ddea3062195ab6e037/tests/test_observability_reconciler.py)).
- A regra é decisão registrada: "Artefatos de app poderão consultar somente `prometheus`, `loki` e `__expr__`" ([infra:`docs/adr/0008-application-observability-reconciliation.md`](https://git.codelab.tec.br/codelab/infra/src/commit/41e02eb8703dc77865ffd1ddea3062195ab6e037/docs/adr/0008-application-observability-reconciliation.md)), repetida no runbook ([infra:`docs/runbook/applications.md`](https://git.codelab.tec.br/codelab/infra/src/commit/41e02eb8703dc77865ffd1ddea3062195ab6e037/docs/runbook/applications.md)), no README da action ([ds:`README.md`](https://git.codelab.tec.br/codelab/deploy-stack/src/commit/fa82c373cb1b4c87135013690ebde72caf28c2c4/README.md)) e no `observability/README.md` deste repositório.
- Rejeição na fase `validate` impede o deploy: "Rejeição ou timeout de dois minutos impede o deploy do runtime" (ADR-0008, Decisão, passo 2); o script falha com "the observability generation is not valid, so the runtime was not deployed" ([ds:`bin/deploy.sh`, linha 209](https://git.codelab.tec.br/codelab/deploy-stack/src/commit/fa82c373cb1b4c87135013690ebde72caf28c2c4/bin/deploy.sh)).
- As datasources da plataforma são provisionadas por arquivo, `platform/grafana/provisioning/datasources/datasources.yml`, montado read-only em `/etc/grafana/provisioning`: `Prometheus` (`uid: prometheus`, padrão) e `Loki` (`uid: loki`), ambas `editable: false` ([infra:`platform/grafana/provisioning/datasources/datasources.yml`](https://git.codelab.tec.br/codelab/infra/src/commit/41e02eb8703dc77865ffd1ddea3062195ab6e037/platform/grafana/provisioning/datasources/datasources.yml); [infra:`platform/grafana/compose.yml`](https://git.codelab.tec.br/codelab/infra/src/commit/41e02eb8703dc77865ffd1ddea3062195ab6e037/platform/grafana/compose.yml)). O arquivo só mudou em dois commits (`ef04693071`, 2026-07-30, e `569bbc1cc7`, 2026-07-31); nunca houve datasource PostgreSQL ali.
- O papel `stack` do Ansible copia os arquivos estáticos e renderiza os `*.j2` de `platform/<stack>/`, então um `datasources.yml.j2` com segredo do vault é mecanismo já usado pela plataforma (por exemplo `provisioning/alerting/contact-points.yaml.j2` e `.env.j2`) ([infra:`ansible/roles/stack/tasks/main.yml`](https://git.codelab.tec.br/codelab/infra/src/commit/41e02eb8703dc77865ffd1ddea3062195ab6e037/ansible/roles/stack/tasks/main.yml)).
- Segredos de Platform Services vivem no Ansible Vault do `codelab/infra`; segredos de runtime de Application Stack vivem nos secrets do Gitea Actions do próprio repositório e só chegam ao `.env` do app via `APPENV_*` ([infra:`docs/adr/0003-application-stack-deploy-contract.md`, emenda de 2026-06-29](https://git.codelab.tec.br/codelab/infra/src/commit/41e02eb8703dc77865ffd1ddea3062195ab6e037/docs/adr/0003-application-stack-deploy-contract.md)). O Grafana não monta `/opt/codelab/apps` nem a dropzone (ADR-0008, Decisão), então um `APPENV_*` nunca chega a ele.
- O papel de monitoramento que já existe, `codelab_monitor`, tem só `pg_monitor` e alimenta o exporter do Alloy, que publica no Prometheus ([infra:`docs/runbook/services.md`](https://git.codelab.tec.br/codelab/infra/src/commit/41e02eb8703dc77865ffd1ddea3062195ab6e037/docs/runbook/services.md); [infra:`platform/alloy/config.alloy`, `prometheus.exporter.postgres "shared"`](https://git.codelab.tec.br/codelab/infra/src/commit/41e02eb8703dc77865ffd1ddea3062195ab6e037/platform/alloy/config.alloy)). O dashboard **Postgres** da plataforma só usa `prometheus` e `loki` ([infra:`platform/grafana/dashboards/postgres.json`](https://git.codelab.tec.br/codelab/infra/src/commit/41e02eb8703dc77865ffd1ddea3062195ab6e037/platform/grafana/dashboards/postgres.json)). Nenhuma peça da plataforma consulta tabelas de app pelo Grafana.
- Do lado deste repositório, a conta de leitura `myhealth_read` existe em produção desde 19/10/2026, e a senha está só no armazenamento privado de senhas do Data Owner, "fora do repositório, do `.env` da API e dos secrets do CI" ([`README.md`, "Provisionar a conta de leitura na VPS CodeLab"](https://git.codelab.tec.br/vctrtvfrrr/myhealth/src/commit/2e9efe4c19db747d9dfbe5a3f4eb756f641c36a2/README.md)). A conta só alcança o schema `read_model` ([ADR `0013`](https://git.codelab.tec.br/vctrtvfrrr/myhealth/src/commit/2e9efe4c19db747d9dfbe5a3f4eb756f641c36a2/docs/adr/0013-grant-read-access-outside-the-migrations.md)).

### Documentação do Grafana

- A datasource PostgreSQL é provisionável por YAML com `type: postgres` (alias de `grafana-postgresql-datasource`), `url`, `user`, `jsonData.database`, `jsonData.sslmode`, `jsonData.postgresVersion` e `secureJsonData.password` ([Configure the PostgreSQL data source](https://grafana.com/docs/grafana/latest/datasources/postgres/configure/)).
- A documentação recomenda um usuário com "only `SELECT` permissions" e avisa que o Grafana "does not validate the safety of queries" ([mesma página](https://grafana.com/docs/grafana/latest/datasources/postgres/configure/)). `myhealth_read` já atende a isso.
- `secureJsonData` é guardado cifrado e não é devolvido aos usuários; `editable: false` impede edição pela UI; arquivos de provisionamento aceitam interpolação de variáveis de ambiente `$VAR`/`${VAR}` ([Provision Grafana](https://grafana.com/docs/grafana/latest/administration/provisioning/)).

### Conclusão (inferência)

Só a plataforma pode declarar a datasource. O caminho coerente com os ADRs da plataforma é um `datasources.yml.j2` no `codelab/infra` com `uid` fixo (por exemplo `myhealth-read`), `editable: false`, `user: myhealth_read`, `database: myhealth` e a senha numa chave do Ansible Vault. Isso exige copiar a senha de `myhealth_read` para o vault da plataforma, o que muda a decisão registrada no README deste repositório de mantê-la só no armazenamento privado do Data Owner. E não basta provisionar: o reconciliador precisa aceitar esse UID, o que é emenda ao ADR-0008.

## 2. Rede: o Grafana alcança `postgres-postgres-1`?

### O que as fontes dizem

- Grafana: redes Docker `web` e `observability`, e porta `127.0.0.1:3000` no host ([infra:`platform/grafana/compose.yml`](https://git.codelab.tec.br/codelab/infra/src/commit/41e02eb8703dc77865ffd1ddea3062195ab6e037/platform/grafana/compose.yml)).
- PostgreSQL: projeto Compose `postgres`, serviço `postgres` (daí o container `postgres-postgres-1`), imagem `codelab/postgres:17.10-trixie-postgis-3`, rede `postgres` e porta `127.0.0.1:5432` no host ([infra:`platform/postgres/compose.yml`](https://git.codelab.tec.br/codelab/infra/src/commit/41e02eb8703dc77865ffd1ddea3062195ab6e037/platform/postgres/compose.yml); [infra:`platform/postgres/Dockerfile`](https://git.codelab.tec.br/codelab/infra/src/commit/41e02eb8703dc77865ffd1ddea3062195ab6e037/platform/postgres/Dockerfile)).
- Quem consome o PostgreSQL entra na rede externa `postgres` e conecta em `postgres:5432`; "O Postgres permanece fora da `web`", e "qualquer app nela enxerga o Postgres e os demais containers ali" ([infra:`docs/adr/0004-shared-postgres-database-provisioning.md`](https://git.codelab.tec.br/codelab/infra/src/commit/41e02eb8703dc77865ffd1ddea3062195ab6e037/docs/adr/0004-shared-postgres-database-provisioning.md)). O mesmo ADR rejeitou acesso por `host.docker.internal`/`127.0.0.1:5432` como "frágil". A API do `myhealth` segue esse padrão (`networks: [web, postgres]` em `compose.yml`; `APPENV_DATABASE_HOST: postgres` em `.gitea/workflows/ci.yml`).
- O exporter de PostgreSQL roda no Alloy, que usa a rede do host (`network_mode: host`), por isso alcança o loopback ([infra:`platform/alloy/compose.yml`](https://git.codelab.tec.br/codelab/infra/src/commit/41e02eb8703dc77865ffd1ddea3062195ab6e037/platform/alloy/compose.yml); [infra:`docs/runbook/observability.md`](https://git.codelab.tec.br/codelab/infra/src/commit/41e02eb8703dc77865ffd1ddea3062195ab6e037/docs/runbook/observability.md)).

### Conclusão

Hoje o Grafana não alcança o PostgreSQL: não compartilham rede, e o `127.0.0.1:5432` do host não é o loopback de um container em bridge. Para alcançá-lo, a plataforma precisaria acrescentar a rede externa `postgres` ao `platform/grafana/compose.yml`; o endereço seria então `postgres:5432` (nome do serviço) ou `postgres-postgres-1:5432`. O PostgreSQL não tem TLS configurado no Compose, então a datasource usaria `sslmode: disable` dentro da rede Docker (inferência).

## 3. `observability/dashboards/*.json`: formato, pasta, UID, título, convergência

### O que as fontes dizem

- **Localização:** `observability/dashboards/*.json`, um dashboard por arquivo; só os `*.json` diretamente no diretório entram (não há recursão), e symlink é recusado ([ds:`README.md`](https://git.codelab.tec.br/codelab/deploy-stack/src/commit/fa82c373cb1b4c87135013690ebde72caf28c2c4/README.md); [ds:`bin/deploy.sh`, linhas 74-95 e 140-150](https://git.codelab.tec.br/codelab/deploy-stack/src/commit/fa82c373cb1b4c87135013690ebde72caf28c2c4/bin/deploy.sh)). A action só valida sintaxe JSON; a semântica é do reconciliador.
- **Formato:** JSON nativo do Grafana (ADR-0008, Decisão), enviado tal qual a `POST /api/dashboards/db` com `overwrite: true` ([reconciliador, `save_dashboard`, linhas 529-534](https://git.codelab.tec.br/codelab/infra/src/commit/41e02eb8703dc77865ffd1ddea3062195ab6e037/ansible/roles/observability_reconciler/files/codelab-observability-reconcile)).
- **UID:** obrigatório e explícito; `[A-Za-z0-9_-]+`; único na geração; reescrito para `<app>--<uid>` e o resultado não pode passar de 40 caracteres, ou seja, até 30 para `myhealth` (linhas 55-60, 111-112, 270-282 e 294-314). Referências a outros dashboards (`dashboardUID`, `dashboardUid`, `__dashboardUid__`) precisam apontar para um dashboard da mesma geração e também são reescritas (linhas 253-267).
- **O que a plataforma impõe ao JSON:** remove `id` e `version`; força `editable: false`; descarta tags que comecem com `codelab-` e acrescenta `codelab-app-myhealth` e `codelab-content-<hash>` (linhas 308-322).
- **Título:** não é tocado nem validado pelo reconciliador. Pastas e títulos de pasta são impostos: UID `codelab-app-<app>`, título `App: <app>` (linhas 103-108; `ensure_folder`, linhas 495-498).
- **Convergência:** o reconciliador é acionado pela troca de ponteiro e por timer de 30 segundos; cria e atualiza antes de remover; dashboard com UID do app ausente da geração corrente é apagado; geração vazia apaga a pasta ([`apply_generation`, linhas 610-660](https://git.codelab.tec.br/codelab/infra/src/commit/41e02eb8703dc77865ffd1ddea3062195ab6e037/ansible/roles/observability_reconciler/files/codelab-observability-reconcile); [infra:`docs/runbook/observability.md`, "Dropzone de aplicações"](https://git.codelab.tec.br/codelab/infra/src/commit/41e02eb8703dc77865ffd1ddea3062195ab6e037/docs/runbook/observability.md)). O `applied` exige dashboard presente, tag de conteúdo esperada, pasta certa e `editable` falso (`verify_generation`, linhas 669-684).
- **Edição na UI:** o ADR-0008 diz que os recursos são read-only na UI e que "Experimentos serão salvos como cópia, exportados e incorporados ao Git". A emenda de 2026-08-03 esclarece que dashboards não têm provenance de provisionamento ("A API de dashboards do Grafana OSS não expõe provenance") e que `editable: false` "entrega o comportamento read-only pretendido sem ser equivalência arquitetural"; a detecção é por marcador de conteúdo e "Não detecta alguém editando pela API e preservando o marcador" ([ADR-0008, emenda](https://git.codelab.tec.br/codelab/infra/src/commit/41e02eb8703dc77865ffd1ddea3062195ab6e037/docs/adr/0008-application-observability-reconciliation.md)).
- **Armadilhas de exportação:** o export padrão do Grafana inclui em `annotations.list` a anotação embutida com `"datasource": {"type": "grafana", "uid": "-- Grafana --"}` ([Dashboard JSON model](https://grafana.com/docs/grafana/latest/dashboards/build-dashboards/view-dashboard-json-model/)). Esse UID não está na lista permitida, então a geração seria rejeitada; o teste do reconciliador rejeita explicitamente o UID `grafana` e o placeholder `${DS_PROMETHEUS}` do "export for sharing externally". Painel com `datasource` nulo é aceito (cai na datasource padrão, Prometheus) (linhas 228-230).

### Conclusão sobre edição na UI (inferência a partir do código)

`apply_generation` só regrava um dashboard quando a tag `codelab-content-<hash>` ou a pasta divergem. Uma edição salva na UI que mude ou remova tags, ou mova o dashboard, é desfeita na próxima passagem (até 30 segundos) e conta como drift. Uma edição que preserve as tags e a pasta não é regravada; se ela também tornar o dashboard editável, `verify_generation` passa a reportar "is editable in the UI" e o recibo `apply` da geração fica `rejected` a cada passagem, sem reparo, até um novo deploy mudar o conteúdo. Não verifiquei na UI do Grafana 13.1 se um dashboard com `editable: false` oferece ao admin um caminho para salvar sobre ele.

## 4. Versão do Grafana, painéis e plugins

- **Versão:** `image: grafana/grafana:13.1` ([infra:`platform/grafana/compose.yml`](https://git.codelab.tec.br/codelab/infra/src/commit/41e02eb8703dc77865ffd1ddea3062195ab6e037/platform/grafana/compose.yml)). A tag fixa minor 13.1 e flutua no patch.
- **Painéis:** a documentação da 13.1 lista como visualizações embutidas, entre outras, Time series ("the default and main graph visualization"), Bar chart, State timeline, Status history, Histogram, Heatmap, Table, Stat, Geomap, XY chart e Trend ([Visualizations, v13.1](https://grafana.com/docs/grafana/v13.1/panels-visualizations/visualizations/)). Os dashboards da própria plataforma usam `schemaVersion` 39 e painéis `stat`, `timeseries` e `logs` ([infra:`platform/grafana/dashboards/postgres.json`](https://git.codelab.tec.br/codelab/infra/src/commit/41e02eb8703dc77865ffd1ddea3062195ab6e037/platform/grafana/dashboards/postgres.json)).
- **PostgreSQL na 13.1:** "Grafana includes a built-in PostgreSQL data source plugin" ([PostgreSQL data source, v13.1](https://grafana.com/docs/grafana/v13.1/datasources/postgres/)). A documentação `latest` informa que, desde a 13.2, ela é um plugin à parte que o Grafana reinstala na versão mais nova a cada reinício, a menos que `preinstall_auto_update = false` ([PostgreSQL data source, latest](https://grafana.com/docs/grafana/latest/datasources/postgres/)). Isso importa se a plataforma subir para a 13.2.
- **Plugins:** o Compose do Grafana não define `GF_PLUGINS_PREINSTALL`, `GF_INSTALL_PLUGINS` nem monta diretório de plugins. Valem os padrões do Grafana, que "installs some suggested plugins on startup" ([Configure Grafana, `[plugins]`](https://grafana.com/docs/grafana/latest/setup-grafana/configure-grafana/)). O reconciliador não valida `type` de painel; um painel de plugin ausente seria aceito pela plataforma e quebraria só na renderização (inferência). Instalar plugin é mudança no `codelab/infra`, nunca no stack.

## 5. Permissões, organização e quem vê

- **Organização:** o reconciliador usa autenticação básica do usuário `admin` (`GRAFANA_USER`, `grafana_admin_user: admin`) sem cabeçalho de organização, e os provisionamentos da plataforma usam `orgId: 1` ([infra:`ansible/roles/observability_reconciler/templates/codelab-observability.env.j2`](https://git.codelab.tec.br/codelab/infra/src/commit/41e02eb8703dc77865ffd1ddea3062195ab6e037/ansible/roles/observability_reconciler/templates/codelab-observability.env.j2); [infra:`ansible/group_vars/vps/main.yml`](https://git.codelab.tec.br/codelab/infra/src/commit/41e02eb8703dc77865ffd1ddea3062195ab6e037/ansible/group_vars/vps/main.yml); [infra:`platform/grafana/provisioning/dashboards/platform.yml`](https://git.codelab.tec.br/codelab/infra/src/commit/41e02eb8703dc77865ffd1ddea3062195ab6e037/platform/grafana/provisioning/dashboards/platform.yml)). Inferência: os dashboards do stack caem na organização corrente do admin, que é a org principal (ID 1).
- **Pasta:** criada por `POST /api/folders` com só `uid` e `title`; o reconciliador não define permissões ([reconciliador, linhas 495-498](https://git.codelab.tec.br/codelab/infra/src/commit/41e02eb8703dc77865ffd1ddea3062195ab6e037/ansible/roles/observability_reconciler/files/codelab-observability-reconcile)). Pela documentação, quem cria uma pasta no topo recebe Admin sobre ela ([Roles and permissions](https://grafana.com/docs/grafana/latest/administration/roles-and-permissions/)), as permissões padrão de pasta dão View ao papel Viewer e Edit ao papel Editor, e "Permissions cannot be set for Admins - they always have access to everything" ([Folder permissions API, v13.1](https://grafana.com/docs/grafana/v13.1/developer-resources/api-reference/http-api/api-legacy/folder_permissions.md)). Dashboards herdam as permissões da pasta ([Manage dashboard permissions](https://grafana.com/docs/grafana/latest/administration/user-management/manage-dashboard-permissions/)).
- **Quem entra no Grafana:** `GF_USERS_ALLOW_SIGN_UP=false`, `GF_AUTH_ANONYMOUS_ENABLED=false`, login por formulário ligado ([infra:`platform/grafana/compose.yml`](https://git.codelab.tec.br/codelab/infra/src/commit/41e02eb8703dc77865ffd1ddea3062195ab6e037/platform/grafana/compose.yml)). Na frente, o Cloudflare Access permite "somente o e-mail do operador", e "O acesso exige autenticação no Cloudflare Access e no Grafana" ([infra:`docs/runbook/external-services.md`](https://git.codelab.tec.br/codelab/infra/src/commit/41e02eb8703dc77865ffd1ddea3062195ab6e037/docs/runbook/external-services.md)). O Traefik ainda aplica `cf-only@file`. Na prática, quem vê os dashboards do stack é o operador; usuários além do `admin` não aparecem em nenhum arquivo do `codelab/infra`.
- **Consequência para dados de saúde (inferência):** uma datasource no Grafana deixa o SQL livre para quem tiver Editor ou Admin na organização (Explore e edição de painel), limitado só pelos grants de `myhealth_read`. O perímetro de um único operador torna isso aceitável hoje, mas qualquer usuário novo na org principal ganharia esse alcance sobre o `read_model`.

## Lacunas e perguntas em aberto

- **Patch exato do Grafana em execução:** a tag é `13.1`; o patch real depende de quando a imagem foi puxada na VPS. Não há acesso à VPS nem à API do Grafana nesta pesquisa.
- **Usuários e organizações reais do Grafana:** os arquivos só mostram o `admin`. Se existem outros usuários ou orgs, e quais papéis têm, só a instância responde.
- **Permissões efetivas da pasta `codelab-app-<app>` no Grafana 13.1:** a documentação da 13.1 descreve as permissões padrão pela API legada e o criador como Admin, mas não afirma explicitamente o que uma pasta recém-criada recebe. Conferir com `GET /api/folders/codelab-app-<app>/permissions` quando houver uma pasta de app.
- **Plugins pré-instalados por padrão:** a documentação manda ler `pkg/setting/setting_plugins.go` e não lista os plugins; não verificado.
- **Edição na UI de um dashboard `editable: false`:** o efeito sobre o reconciliador foi deduzido do código, não observado; não verifiquei se a UI da 13.1 deixa o admin salvar sobre ele.
- **Desenho da mudança na plataforma:** nenhum ADR do `codelab/infra` trata de datasource SQL por app. Ficam para o mapa #69 e para o dono da plataforma: (a) se o Grafana entra na rede `postgres`, ampliando o alcance dele a todas as databases do PostgreSQL compartilhado; (b) se a lista permitida passa a ser por app (só `myhealth` consulta `myhealth-read`) ou global; (c) se a senha de `myhealth_read` vai para o Ansible Vault, revendo a decisão do README de mantê-la só com o Data Owner, ou se a plataforma cria um papel próprio para o Grafana.
- **Alternativa sem datasource SQL:** expor métricas Prometheus pelo opt-in do ADR-0012 cabe no contrato atual, mas o runbook avisa que o endpoint de métricas "usa HTTP sem autenticação. Não exponha secrets nem dados pessoais" ([infra:`docs/runbook/applications.md`](https://git.codelab.tec.br/codelab/infra/src/commit/41e02eb8703dc77865ffd1ddea3062195ab6e037/docs/runbook/applications.md)), e o limite de 10.000 amostras por scrape não comporta um histórico. Não serve para a Personal Health History.
