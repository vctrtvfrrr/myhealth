# Project the Current Health Record with one shared statement

The Current Health Record is a row saying which Observed Record Version is the latest known state of a Health Record, written by a single SQL function that recomputes it from the preserved versions of the identities given to it. The ingestion calls that function for the identities it observed, inside its own transaction; the rebuild subcommand discards the table and calls the same function for every identity. A projection and its reconstruction cannot drift when they are the same statement over a different set of identities, which is what the requirement "the rebuild is identical to the incremental projection" asks for and what a second implementation in Kotlin would only promise.

Recomputing, rather than comparing the arriving observation against the projected one, is what makes a late import harmless: an observation that reaches the API after a newer one was already projected does not become current, because currency is decided over all preserved versions and not over arrival order.

The function locks the Health Record Identity rows before recomputing. An ingestion already holds them, from the upsert that resolved the identity of every item it wrote, so the lock is there for the caller that wrote nothing: without it the rebuild would recompute while an ingestion commits a newer version underneath it, and would project the version it happened to read. The order is stable so that the two paths ask for rows the same way, and that is all it buys. It is not what keeps concurrent ingestions from deadlocking, and nothing in this projection could be: a batch takes its identity locks in the order its items arrive, before the projection is reached, so two batches carrying the same Health Records in opposite orders can deadlock — as they already could before any of this existed. The loser is rolled back whole and answered `503`, which the ingestion is idempotent under and the application retries.

The projection stores no copy of the version's content. Every field a reader wants already exists on the immutable row it points at, so copying them here would create a second, divergeable representation of something that cannot change, and the per-vertical read views join instead. The cost is a join on every read, which is what a personal history's volume can afford.

Projecting inside the ingestion transaction was chosen over a background worker: a `200` already means the observation is durable, and the Data Owner would otherwise be told an observation is stored while the state they query still hides it. The cost is that a projection failure fails the ingestion, which is correct here — both belong to the same promise.
