# Derive availability and permission state from observations

Samsung Health Availability is read from the outcome of a real SDK operation, never from a persisted connection flag and never from a separate availability probe. Answering the permission query at all is what makes the platform ready, so asking availability first would mean a second round trip that can disagree with the query it precedes. Each failure is classified into remediation, temporary unavailability or definitive lack of support, and an outcome the adapter does not recognize stays temporary: silently promoting an unknown error to unsupported would tell the Data Owner the device can never work.

The SDK reports only the currently granted set, so denied and revoked are local inferences. Room keeps, per Health Category, whether a request was ever observed, whether a grant was ever observed, whether the last observation showed it granted, and when that observation happened. Denied is a completed request whose category is absent from the granted set; revoked is a category that was granted before and is absent now. After a reinstall or a data wipe the application claims no history it lost: categories Samsung Health still reports appear granted and every other one returns to not requested.

A check is atomic. All cataloged categories are written in one Room transaction and only after a successful query, so a failed query leaves every Permission State untouched and the previous observation stays visible as outdated. Before the first successful check there is an unknown query state, which is not a fifth Permission State.

A request observed in this process is written together with the observation that shows its effect, not on its own. Persisting it earlier would flip a category to denied without an observation behind it; the accepted cost is that a request whose process dies before the next successful query is forgotten, and the category reappears as not requested until it is requested again.
