# Conclude a removal from a declared inventory

ADR 0017 left one divergence open: a Health Record removed at the source while the application was not watching stays projected as present forever, because no read reports an absence except the changes feed, and the feed only reports what happened while it was being read. Version 2 of the ingestion contract closes it by letting the application declare what it saw. A batch may carry a Record Inventory: a stretch of local time, the instant its read began, and every Samsung UID of the batch's record type read there. The API concludes that a Health Record it holds as present, whose period starts inside the stretch in its own local time, which it knew of before that read began, and which the inventory leaves out, was removed at the source. The conclusion is an Observed Record Version of removal like any other, and nothing preserved is touched.

The stretch is per page of the history walk, not per walk. A page ends at the last local start it holds, which is left out of the stretch because a later page may still hold records sharing it; the page the window ends with reaches the end of the window. The records already read at the start of a stretch are carried on the Sync Cursor, durably, because a walk resumed from a page token continues after them and would otherwise declare their stretch without them. Per page bounds the size of a declaration — a declaration per walk would name the whole history of a category in one request — and every read the application already makes declares without a new read: the initial load, the daily overlap, a full reconciliation and a reinstallation's walk all cover their stretches again.

Leaving a record out of a stretch is a removal, and naming one outside it costs nothing. Every rule here falls on that side. A page declares every record it read, including those at its end. An inventory is held on the device and sent only once nothing read is still waiting in the Outbox, so every observation of its stretch is either stored or a Mapping Pendency; the API answers an inventory naming an identity it never stored as `incomplete` and concludes nothing from it, because what it leaves out may simply not have arrived. A record the API learned of only after the read began — created during the walk and delivered by the changes feed — proves nothing by its absence and is left alone. An inventory the API answered is dropped whatever it concluded: sending it again would get the same answer, and the next read of the stretch declares it anew.

The removal is dated like the version it supersedes, not by when the absence was seen. It wins that version's tie in the projection of ADR 0012 by arriving later, and it loses to any edit the source made afterwards. A removal concluded in error — the API had not yet learned that a record moved out of the stretch when the inventory arrived — is therefore undone by the observation of that move rather than outliving it. Dating it by the inventory would make a later edit lose, and would also render a new version of the same absence on every inventory. As it is, the rendering depends only on the version it ends, so a repeated inventory either finds nothing present to conclude or stores nothing new. The removal carries the version's period, unknown Source Provenance, and `concludedBy: declared_absence`, which keeps it apart from a removal the feed reported. Which inventory concluded it is kept beside it.

The interval is local time, start included and end excluded, because local time is what a history read filters on; the API compares it against the version's period start shifted by its own recorded offset. Version 1 stays accepted and unchanged: a batch declaring version 1 concludes nothing, and whatever it carries under `inventory` is an unknown property like any other. An application on version 2 needs an API that speaks it, which is the order ADR 0007 already deploys in.

This is hard to reverse. Removals concluded this way become part of the Personal Health History, the wire shape is published, and the cursor on the device carries what the walk read at its edge. A different design — inventories per walk, or the API keeping its own index of what each device saw — would have to coexist with versions already concluded under this one.
