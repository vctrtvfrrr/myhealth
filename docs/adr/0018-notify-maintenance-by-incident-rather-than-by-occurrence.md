# Notify maintenance by incident rather than by occurrence

The synchronization runs about twenty-four times a day without anyone watching it, and some of what it meets there is not something it can resolve: a record the API refuses, a constant no mapper interprets, a contract neither side accepts, a read permission that was granted and taken away, a stored position no build can read, a Samsung Health this build cannot serve. Each of those needs a change to the code, and the Data Owner is the only person who can make it. Reporting them as they happen would mean one notification per run of a condition that will still be there on the next one, so the code stops being read and the channel stops being useful.

An incident is therefore identified by what has to be fixed, never by the moment it was met. The identity is the code, the Health Category when fixing one category leaves the others alone, and a detail that tells apart two incidents of the same code — the rejection codes of a refusal, the enum field and constant of a gap. Everything wider is reported without a category, so a single thing to fix stays a single notification however many categories meet it. Meeting the condition again updates the same row and replaces the same notification, which is what the Android tag is for: the count and the last occurrence move, and nothing is added beside it. The table holds what is currently wrong rather than a log of every time it happened, which also means it never grows with the history.

What is open is what is currently wrong, so an incident is ended by the run that observes its condition gone. Samsung Health answering ends the unsupported platform; a granted permission ends the revocation; a category that read and delivered ends the position it had lost and the contract neither side accepted. Nothing is kept as resolved, and the condition returning is a new incident dated by its own first occurrence. An incident left open after its cause was fixed would be worse than no channel at all: the screen would keep asking for a change to code that no longer needs one, and the Data Owner would learn to disbelieve it. A refused record and an enum gap are the exception, and stay open until the mapper changes — the observation behind them is still in the Outbox, out of every batch.

Where an incident and the state that produced it cannot be written together, the incident is written first. Rejecting an item takes it out of every later batch and re-reading an unrecoverable position replaces it, so both conditions happen once; a process death between the two writes would leave one of them unreported for good, while the other order costs a re-report the identity absorbs as one more occurrence. The two live in separate Room databases and the notification is not a database at all, so this ordering is what is available rather than atomicity. What remains uncovered is a death between writing an incident and posting it, which loses one notification of an incident the diagnostics screen still shows.

A transient failure is held instead. Reaching neither Samsung Health nor the ingestion API is ordinary on a phone, and the first hour of it says nothing about the code. It is recorded from the first occurrence, because that is what dates the start of the outage, and it becomes a notification only once a whole day has passed without any synchronization getting through. A run in which any category succeeded ends every transient incident and forgets it, so the day is counted from the last success rather than from the first failure ever seen. An outage that starts again starts the day over.

Not everything a run cannot finish is an incident. An ingestion endpoint that was never configured is waiting on the Data Owner, and an Outbox at its limit is backpressure working as designed. Reporting either as needing attention to the code would be telling the Data Owner to fix the wrong thing. A permission that was never granted is the same case, which is why only a revocation is reported.

An incident carries nothing that was observed. The detail is drawn from vocabularies the code itself defines, and the enum audit only reads fields a mapper declared as enums. Declaring a field says which one is read and not what the source may put in it, though, and what arrives there is unexpected by definition — that is why it is being reported. So the value is checked against the shape of an SDK constant rather than trusted, and a value outside it is reported as the bare field name: the maintainer still learns where to look, and free text, a coordinate, a token, an unbounded string or the separator the identity is built out of never reaches the table, the notification tag or the screen. That is a rule about where the data lives, not about taste: a diagnostic that quoted the reading, the device it came from or the token that delivered it would be another copy of the Personal Health History, kept in a notification and a screen that nothing protects. The failure detail behind an incident is discarded for the same reason, and the code plus the suggested action is what remains — which is what a maintainer needs anyway, since the fix is in the code and not in the record.
